# ROOK 보행 / 하네스·스킬 검토 — 2026-09-12

결론: 현재 ROOK의 보행 완료 판정은 철회 대상이다. 실제 원화의 반대발 접지와
보행 연결이 실패했는데, 프레임 다양성·입력 검사 및 자유서술 승인 기록이 이를
막지 못했다. 이 검토는 원인 조사이며, 원화·렌더러·스킬의 수정 완료 보고가 아니다.

## 발견 사항

### 1. P1 — 원화가 반대발 접지 순환을 충족하지 않는다

빌드 시트 경로:
`qa/build_candidates/rook/c643f1ce2c9e4208a53222beea6a5eb6/reference/atlas/rook/`.

- `SE_walk_keyframes.png`: 0번과 3번은 반대발 접지여야 하지만 앞/뒤 다리의
  배치가 반복된다. 탄약통이 있는 허벅지의 연결과 지지 역할을 따라가면
  0–4번에서 제대로 된 반대 지지 전환과 통과 자세를 확인할 수 없다.
- `N_walk_keyframes.png`: 0번과 3번 모두 같은 쪽 다리가 길게 뒤로 남는다.
  발바닥 노출과 무릎 각도만 조금 바뀌며, 양쪽 발로 체중을 넘기는 한 주기가 없다.
- 실제 영상의 2.407초(frame 0)와 3.001초(frame 3)에서도 SE 다리 배치 반복이
  확인된다. 바닥과 배경은 이동하는데 기대하는 반대 접지로 바뀌지 않는다.
- E 시트도 연결을 재검토해야 한다. 개별 자세의 완성도와 반대 위상으로 연결되는
  동작의 완성도는 다르다. 모든 방향의 모든 프레임을 이번에 재승인하지 않았다.

이 문제는 이전 ASTER의 프레임 5 고정/구형 분절 다리 로딩 버그와 다르다.
현재 ROOK는 올바른 공통 렌더러로 잘못된 보행 원화를 순서대로 표시한다.
템포나 이동 속도만 바꿔서는 누락된 반대발 자세를 만들 수 없다.

### 2. P1 — 40행 검증은 보행 순서·접지·미끄러짐을 검증하지 않는다

`public/qa/locomotion-checks.js`는 선택된 하체 이미지의 해시가 6개 이상인지,
프레임 번호가 모두 관측됐는지, 이동 거리와 발사 횟수가 조건을 만족하는지 검사한다.
서로 조금 다른 같은 자세도 이 조건을 만족할 수 있다.

`locomotion_review.py:16`은 프레임·해시를 집합으로 바꾸고, 시간 순서와 위치를
재계산하지 않는다. 별도의 보존된 실제 보고서에 대해 `probe_validator.py`를 실행했다.
메모리 복제본만 바꿨으며 원본 QA 보고서는 수정하지 않았다.

| 입력 | 현재 검증기 결과 |
| --- | --- |
| 실제 원본 보고서 | 통과 |
| 프레임 번호를 0→0, 1→3, 2→1, 3→4, 4→2, 5→5로 뒤섞음 | 통과 |
| 모든 샘플의 시간·위상·위치를 0으로 고정하고 기존 이동거리 요약을 남김 | 통과 |

이는 실제 보고서가 조작됐다는 주장이 아니다. 잘못된 결과를 거부해야 할 검증기의
누락을 재현한 것이다. 발의 해부학적 의미는 이 기술 검사와 별도로 검토해야 한다.

### 3. P1 — E 한 주기 승인 후 확장하는 절차가 실행 조건이 아니다

`character_workflow.py:12,87`의 PILOT은 E idle/0, walk/0, walk/3의 작업 우선순위뿐이다.
E 0–5 전체의 순환, 반대발 연결, 실제 속도 재생 승인 기록을 요구하는 단계는 없다.
`source_status()`는 개별 슬롯 승인만 모아 ready를 계산한다.

`review_source()`는 검토자와 메모가 비어 있지 않고 증거 파일이 있으면 승인 기록을
작성한다. 오른발/왼발 역할, 0↔3·1↔4·2↔5 대응, 5→0 연결을 구조적으로 기록하거나
검증하지 않는다. 문서의 “E cycle을 먼저 검토” 지침을 놓쳐도 양산을 진행할 수 있다.

### 4. P1 — 최종 승인이 실제 동작 관찰을 강제하지 못했고, 승인 내용도 부족했다

`character_workflow.py:155` 이후의 승인 경로는 영상 크기·길이·해시·메타데이터와
자유서술 메모를 받는다. `cap.read()`는 한 프레임을 읽는다. 별도 해상도 validator의
전체 디코딩 성공도 미끄러짐이나 해부학적 연결의 승인 근거가 되지 않는다.

기존 `qa/rook/runtime_reviews.json`의 승인은 접지·무기 자세에 대한 일반 설명과
40/17 테스트 통과, 영상 해상도·프레임 수를 적었지만, 실패한 SE/N의 반대발 전환이나
시간대별 발 관찰을 제시하지 않았다. 이 상태에서 REVIEWED_DELIVERY와 보행 완료를
보고한 것은 잘못된 승인 판단이다. 같은 모델의 자유서술만으로 다시 재승인하면 반복된다.

### 5. P1 — 인계는 런타임 거절을 읽어도 다음 작업으로 반영하지 않는다

`character_handoff.py:59`는 runtime_reviews 및 delivery 파일을 해시에 포함한다.
그러나 `nextAction` 결정은 source_status에 의존하고, 소스가 ready면
`BUILD_REVIEWED_SOURCES`가 된다(:104–105). 런타임 보행 거절을 우선 해결하는
상태 분기가 없다. 현재 사용자 거절을 기록해도 소스 승인이 유지되는 한, 다음 작업자가
같은 원화를 재빌드하도록 유도될 수 있다.

### 6. P2 — 스킬과 생성기의 위상 정의가 서로 다르다

`references/gait-repair.md:18`은 1/4를 passing, 2/5를 swing으로 설명한다.
`new_character.py:7`과 ROOK requests는 1/4를 뒤로 드는 swing,
2/5를 무릎이 앞으로 통과하는 passing으로 설명한다.
번호의 의미를 한 계약으로 통일해야 한다. 현재는 생성과 검토가 다른 기준을 읽을 수 있다.

requests에 poseGuide 경로가 있어도 각 소스 승인에는 실제 사용한 가이드·위상 계약의
해시가 필수로 묶이지 않는다. 예를 들어 N/walk/3의 저장된 tool-response에는
`referencePaths: [motion_lab_v1/art/rook/N_walk_2_master.png]`만 기록돼 있다.
이 기록만으로 정확한 UAL 가이드가 실제 생성에 전달됐다고 검증할 수 없다.

### 7. P2 — 기존 템포 개선이 새 캐릭터에 전달되지 않았다

ASTER walk에는 `phaseStarts: [0, .2, .33, .5, .7, .83]`가 있다.
ROOK에는 없으며 현재 브라우저 프로필에서도 확인했다.
`new_character.py:18–21`은 MICA 기본값을 복사한 뒤 clips를 frames 값만으로 다시 만든다.
따라서 런타임에 타이밍 기능이 있어도 새 레시피는 균등 분할로 돌아간다.

ROOK 기본 걷기는 1.35/1.6 = 약 0.844주기/초, 6장 기준 약 5.06장/초다.
달리기는 별도 run 원화 없이 같은 walk를 약 8.62장/초로 재생한다.
정확한 접지 곡선은 새 캐릭터의 보폭과 실제 프레임에 맞춰 검증해야 하므로
ASTER 값을 무조건 복사하는 것만으로 해결됐다고 할 수 없다.

### 8. P2 — 정렬 기준도 발 접지를 보장하지 않는다

`build_atlas.py:48–54`는 매 이미지의 불투명 전체 높이를 656px로 맞추고
가장 낮은 픽셀을 공통 바닥에, 추정한 수평 기준점을 root에 맞춘다.
실제 골반·발바닥·접지 시간·월드 이동을 연결한 정렬은 아니다.
크기 보정·방향별 투영과 별개로 발 접지/미끄러짐을 평가해야 한다.
이 항목은 이번 SE/N 반복 지지의 원인과 구분되는 구조적 취약점이다.

## 수정해야 하는 순서

1. 사용자 거절을 현재 런타임 검토에 기록하고 이전 완료 판정을 HOLD로 무효화한다.
2. 위상 의미를 한 계약으로 통일하고, 캐릭터별 좌우 신체 표식과 접지 역할을 정의한다.
3. E 한 방향 전체의 반복 재생·반대발·루프 연결 검토를 확장 전 필수 단계로 구현한다.
   파일 6개 또는 서로 다른 해시 6개는 그 승인이 아니다.
4. 동영상의 시간대별 관찰·실제 발 좌표 및 이동량을 묶어 검토한다. 기술 검사는
   프레임 순서, 시간 증가, 위치에서 재계산한 거리, 루프 연결을 검증해야 한다.
   주관적 자연스러움과 좌우 다리 판독을 기술 PASS로 대신하지 않는다.
5. runtime repair를 handoff의 우선 작업으로 전달하고 전체 주기 거절을 source-ready가
   덮지 못하게 한다. 실패 예제를 거부하는 회귀 검사를 추가한다.
6. 검증된 E 절차로 실패 방향의 원화를 수리하고, 실제 속도와 발 보폭을 맞춘 뒤
   같은 패키지의 이동/사격 영상을 다시 검토한다. 속도 조절은 누락 자세의 대체가 아니다.

현재 코드에는 Luna 전용 렌더러 분기가 없다. 관찰된 실패는 생성된 다리 자세를 잘못
승인했고 이를 차단할 강제 단계가 빠졌다는 것이다. 모델 이름만으로 발생 원인이나
다른 모델의 무실패를 단정할 근거는 없다. 이 검토는 하네스의 수리 또는 재생성 성공을
의미하지 않으며, 원본·실패 자료·종전 검토 이력은 보존한다.
