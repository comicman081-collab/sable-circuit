## 측정 방법 (`.cache/session/web_fps_probe.py`, `web_fps_ab.py`)
- 브라우저: 보이는 Edge 창, DevTools로 조작했다. 1920×1080, 배율 1. GPU는 ANGLE D3D11 RTX 4070 SUPER. HTTP 캐시는 껐다.
- 흐름: 타이틀 → 인트로 건너뛰기 → 기지 → 브리핑 → 작전 1 출격 → 14초 동안 이동하며 사격 → 6초 더.
- 측정값: requestAnimationFrame 간격, WebGL 컨텍스트 손실, 페이지 오류.
- 앱 안의 실제 입력만 썼고, 테스트용 조작 기능은 쓰지 않았다.
- 측정 중 드러난 문제 두 가지를 고쳤다.
  - 이 컴퓨터의 다른 자동화 세션이 같은 DevTools 포트(9333)를 써서, 측정 창이 다른 프로젝트 페이지로 넘어간 적이 있었다.
    - 이제 빈 포트를 골라 쓰고, 그 포트를 연 프로세스가 직접 띄운 Edge인지 확인한다.
    - 실행이 끝날 때 페이지 주소가 측정 대상 그대로인지 기록한다. 아래 모든 실행이 그대로였다.
  - 캐시를 끄면 로딩 중 메인 스레드가 멈춘다. 그래서 프레임이 3초간 안정된 뒤에 재기 시작한다.

## 웹이 느린 이유 (`web_combat_cpu_profile_summary.json`)
- 전투 중 메인 스레드는 거의 100% 스크립트 실행이다. GPU가 아니라 브라우저 메인 스레드의 일이 프레임을 정한다.
  - 여기에는 wasm 게임 루프와 WebGL 호출이 들어간다.
- 전투 11초 CPU 프로파일에서 자기 시간이 가장 긴 항목:
  - wasm 함수 하나(`wasm-function[2238]`)가 38.8%다.
    - 이 빌드의 wasm에는 이름 정보가 없어 어떤 함수인지는 확인하지 못했다.
    - 한 함수에 몰려 있는 모양은 GDScript 인터프리터 루프일 때와 맞지만, 확인은 아니다.
  - WebGL `getParameter`가 18.9%다. 동기식이라 느린 조회인데 매 프레임 많이 불린다.
  - VAO와 버퍼를 매 프레임 만들고 지운다(`createVertexArray` / `deleteVertexArray` / `createBuffer` / `bufferData`).
    - Godot 호환 렌더러는 캔버스 다각형을 다시 그릴 때마다 이것들을 새로 만든다.
- 네 빌드에 공통이므로 이번 변경과 무관한 기존 성능이다. 개선은 따로 할 일이다.
  - 다음 단계: 이름 정보가 있는 웹 빌드로 프로파일을 다시 떠서 원인 함수를 찾는다. 매 프레임 다각형을 다시 그리는 노드와 `getParameter` 호출처를 줄인다.
